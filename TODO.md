## Mejoras conocidas / deuda técnica

- [ ] Los iconos de `public/icons/*.svg` son un placeholder (monograma "NB"); sustituir por un diseño real cuando se defina la identidad visual de la app.
- [ ] El "objetivo del mes" (sección 7, tarjetas "Ahorrar este mes") sigue siendo solo una referencia visual — no se aplica ni se recuerda automáticamente. Si en el futuro se quiere avisar cuando el usuario no ha destinado suficiente dinero real a un objetivo ese mes, haría falta comparar `aportaciones_objetivo` del mes en curso contra `calcularAportacionDeseada`.
- [ ] La asignación de un gasto de "Ahorro" a un objetivo solo se puede hacer sobre movimientos propios (`usuario_id` = usuario de la sesión), nunca "a nombre del otro" — por las políticas RLS de `objetivos_ahorro` (individuales, sección 7), la sesión activa no puede ver los objetivos del otro usuario para poder elegirlos.
- [ ] Tipos de `src/lib/supabase/database.types.ts` están escritos a mano porque no hay CLI de Supabase autenticado en este entorno. Cuando se disponga de `supabase login`, regenerar con:
      `npx supabase gen types typescript --project-id koyvpbsnrxqheaugkxbu --schema public > src/lib/supabase/database.types.ts`
- [ ] `npm audit` reporta un aviso "high" sobre `react-router-dom` (GHSA-qwww-vcr4-c8h2, CSRF en "RSC Mode"). No aplica a esta app: es una SPA client-side con `HashRouter`, sin React Server Components ni server actions. Revisar si sale una versión >8.2.0 que lo resuelva sin downgrade.
- [ ] Sin tests de integración de RLS todavía (ver sección "Verificación end-to-end" del plan de arquitectura: probar con las 2 cuentas reales que `privado`/`compartido` se respeta).
- [ ] La selección de "líneas" en Visualizaciones vive en un contexto de React montado en `AppShell` (`lib/visualizaciones/VisualizacionesProvider.tsx`): sobrevive a cambiar de pestaña dentro de la misma sesión, pero se pierde al cerrar/recargar la app (a propósito, no se persiste en `localStorage`). Si en el futuro se quiere que sobreviva también a cerrar la app, sería cuestión de guardar ese mismo estado en `localStorage`.
- [ ] El límite de 8 líneas en Visualizaciones es deliberado: es el techo real de la paleta categórica validada por daltonismo/contraste (ver `src/components/charts/colorsCategoricos.ts`). No se puede subir más sin repetir color entre dos líneas — si hiciera falta más, habría que rediseñar como tabla o pequeños múltiplos en vez de generar más colores.
- [ ] Tras cada despliegue, la web puede tardar unos minutos (hasta ~10) en reflejar los cambios: la CDN de GitHub Pages cachea `index.html`/`sw.js` hasta 10 minutos (`Cache-Control: max-age=600`, no configurable desde este repo), y encima el service worker de la PWA tiene que darse cuenta de que hay una versión nueva. Se mitigó parcialmente registrando el SW a mano en `main.tsx` con una comprobación de actualización cada minuto (antes solo se comprobaba en momentos puntuales), pero el límite de la CDN no se puede eliminar sin cambiar de hosting.
- [ ] El deploy a GitHub Pages puede fallar de forma puntual quedándose en "deployment_queued" hasta hacer timeout (visto el 2026-08-06, resuelto solo al reintentar `gh workflow run deploy.yml` unos minutos después). Parece un atasco temporal del backend de Pages, no relacionado con el código — si vuelve a pasar, reintentar pasados unos minutos.
- [ ] Los periodos de "mes" personalizado (sección 3, `es_primer_dia_mes`) se recalculan siempre a partir de las nóminas marcadas actuales: si se edita la fecha de una nómina marcada, se desmarca la casilla, o se borra ese movimiento, los rangos de los meses que dependían de esa marca cambian retroactivamente (a diferencia del mes de calendario fijo de antes). Es un comportamiento intencionado del diseño, no un bug, pero puede hacer que un gráfico de Visualizaciones ya visto cambie tras editar una nómina antigua.
- [ ] Patrimonio (sección 15): el "Precio Actual" de cada posición se actualiza a mano por ahora — sin integración de mercado en tiempo real (se descartó scraping desde el cliente por CORS; automatizarlo requeriría una Edge Function de Supabase + `pg_cron`, pospuesto a una fase futura).
- [ ] El backfill del histórico de Patrimonio (`generar_snapshot_patrimonio`) para posiciones SIN tae rellena los días saltados usando el precio actual VIGENTE en el momento de ejecutarse, no el valor real que tuviera la posición ese día pasado — no se guarda un histórico de precios de mercado independiente, así que no hay forma de saber el valor exacto de un día no visitado. Si se añade una posición con una fecha de compra muy antigua, el histórico retroactivo saldrá como una línea plana al precio actual hasta que se empiece a actualizar el precio día a día. Las posiciones CON tae no tienen este problema: la fórmula de interés permite calcular el valor exacto de cualquier día pasado.
- [ ] El snapshot diario de Patrimonio no se reescribe una vez generado ese día: si editas el "Precio Actual" (o la TAE/importe base) de una posición después de que la app ya haya generado el snapshot de hoy, el punto de "hoy" en el histórico se queda con el valor anterior hasta el snapshot de mañana (aunque el total en vivo de la página ya refleje el cambio).
- [ ] La TAE de Fondo Monetario/Cuenta Remunerada/Cuenta de Ahorro calcula el valor actual siempre desde `fecha_compra` con el `precio_compra_unitario` guardado: si se edita ese importe más adelante (p. ej. para reflejar una aportación adicional a la misma cuenta), el cálculo se reinicia con el nuevo importe desde la fecha de compra original, sobrestimando el interés ya devengado antes de esa aportación. Para varias aportaciones en momentos distintos a la misma cuenta remunerada, crear una posición separada por cada una en vez de editar el importe de una existente.
